**Status:** Approved in conversation; awaiting review of this written specification

## Objective

Add a recruiter- and hiring-manager-focused static case study to Made by Hakim that demonstrates the engineering behind Budget V2 without publishing private financial data, source code or a downloadable workbook.

The primary takeaway for a reader scanning the page for roughly one minute should be that Budget V2 is a carefully bounded data-engineering system: it preserves source evidence, uses deterministic financial semantics, exposes uncertainty for review and reconciles outputs before presenting them.

## Success criteria

- A dedicated Gatsby page is available locally at `/projects/budget-v2/` and is linked from the existing Projects catalogue.
- The page leads with data integrity, deterministic processing and reconciliation rather than personal-finance product features.
- Three or four static screenshots are generated by the real Budget V2 workflow using a separate, entirely synthetic dataset.
- Every public visual and amount is visibly synthetic and contains no real or real-derived financial data.
- The architecture, decisions, limitations and claims are supported by the current Budget V2 documentation and implementation.
- The case study is responsive, accessible and consistent with the existing Made by Hakim visual language.
- Local builds and tests pass in both repositories.
- Nothing is committed, pushed, deployed or published without separate explicit approval.

## Non-goals

The first pilot will not include:

- a real workbook, real-derived values or private screenshots;
- transaction-level or merchant-level personal data;
- a downloadable workbook or synthetic dataset;
- a public Budget V2 repository or source-code link;
- an interactive dashboard, backend, API or authentication;
- live bank integrations or Open Banking;
- a productised SaaS experience;
- speculative claims about unfinished work;
- deployment, publication or external sharing.

Monthly analytics and guarded email delivery may appear only as a brief downstream-output note. They are not the focus of the case study.

## Repository boundaries

### Budget V2

Budget V2 remains the private implementation source of truth. It supplies a deterministic synthetic demonstration run using the real schema and processing path.

The existing checkout contains substantial uncommitted work. Showcase implementation must preserve it, avoid unrelated edits and prefer additive files or narrowly scoped changes. It must not assume that the last commit represents the current system.

### Made by Hakim

Made by Hakim contains only reviewed public derivatives:

- the static Gatsby case-study page;
- three or four optimised synthetic screenshots;
- a static architecture graphic or accessible HTML/CSS diagram;
- concise, evidence-backed prose;
- the catalogue entry and the smallest reusable link-label extension needed by `ProjectCard`.

No private Budget V2 input, output, configuration or source code crosses into this repository.

## Architecture and data flow

```text
Synthetic provider files
        |
        v
Isolated temporary PostgreSQL database
        |
        v
Existing import -> canonicalise -> enrich/review -> reconcile flow
        |
        v
Existing workbook extraction and preview rendering
        |
        v
Local manual accuracy and privacy review
        |
        v
Selected static WebP images
        |
        v
Made by Hakim case-study page
```

The public page has no runtime dependency on Budget V2. It is a static consumer of reviewed images and prose.

## Synthetic demonstration workflow

The private repository will gain a small, deterministic fixture containing only visibly fictional accounts, descriptions, dates and amounts. A dedicated command will:

1. Validate that every input comes from the showcase fixture directory.
2. Create a temporary PostgreSQL database with an unmistakable showcase-only name.
3. Apply the existing Budget V2 schema.
4. Run the existing ingestion, canonicalisation, categorisation/review and reconciliation path.
5. Extract workbook data and invoke the existing workbook builder and preview renderer.
6. Write generated files under an ignored local showcase-output directory.
7. Clean up the temporary database even if generation fails.

The command must reject the normal Budget V2 database and any database name outside the dedicated showcase pattern. It must not read the accepted V1 workbook, live provider inboxes, production outputs or local private configuration beyond the minimum PostgreSQL administration connection required to create and remove the temporary database.

Generated images do not move into Made by Hakim automatically. The implementation workflow includes an explicit local review before selected images are copied across the repository boundary.

## Public page structure

The page uses the approved evidence-led order:

1. **Hero:** “Building a trustworthy personal-finance data pipeline”, a concise summary and a prominent synthetic-demonstration disclosure.
2. **Problem:** why overlapping provider files, transfers, refunds and incomplete history make naive totals unreliable.
3. **Constraints:** exact money arithmetic, immutable source evidence, explicit review and no guessed financial facts.
4. **Architecture:** a schematic provider-files-to-outputs flow with concise boundary annotations.
5. **Workflow proof:** four short sections covering ingestion/canonicalisation, categorisation/review, reconciliation and generated outputs. Each section pairs one engineering point with a synthetic screenshot.
6. **Engineering decisions:** integer minor units, stable identities, provider-versus-economic transaction semantics, explicit classification precedence and safe transfer matching.
7. **Limitations:** synthetic public evidence, file-based connectors, incomplete historical source limits and deliberately excluded product features.
8. **Lessons:** auditability, explicit uncertainty and generated interfaces as consumers rather than sources of truth.
9. **Downstream note:** one short mention of monthly analytics and guarded email drafts.
10. **Call to action:** the existing web-based Experience record and LinkedIn destination; no downloadable CV, new form or data collection.

## Public content contract

The hero and every evidence image will state that the demonstration is synthetic. A standard caption such as “Synthetic demonstration generated by Budget V2” will make provenance unambiguous.

Public copy must:

- describe only capabilities verified in current documentation and implementation;
- present Budget V2 as a personal, locally operated engineering system rather than a commercial or production-scale banking platform;
- contain no real or real-derived totals, dates, merchants, account names, classifications or screenshots;
- avoid unmeasured performance, security, adoption or reliability claims;
- explain unresolved cases as deliberate review boundaries;
- describe excluded ideas as exclusions, not promises or “coming soon” features;
- provide no private-repository or download link;
- use concise problem -> decision -> evidence -> consequence prose.

Captions must explain what an image proves rather than merely describe its appearance.

## Failure handling and privacy controls

The synthetic generator fails closed when:

- the target database name is outside the showcase-only pattern;
- an input path leaves the synthetic-fixture directory;
- schema application, import, enrichment, reconciliation, extraction or rendering fails;
- expected workbook sheets or preview images are missing;
- a configured synthetic marker or privacy check fails.

Temporary-database cleanup runs in a guaranteed cleanup path. Generated workbooks, intermediate JSON and previews remain ignored local artefacts. Public images cross repositories only after manual review.

Automated privacy checks are defence in depth, not a substitute for human review. Final acceptance requires inspecting every candidate public image and all public copy before any commit or publication decision.

## Verification

### Budget V2

The smallest meaningful automated check will prove that the synthetic demonstration:

- exercises ingestion, canonicalisation, categorisation/review and reconciliation;
- can run repeatedly without duplicating canonical transactions;
- retains exact signed integer-minor-unit arithmetic;
- produces the expected workbook sheets and selected preview images;
- uses only fixture-controlled synthetic identifiers and contains no known private path or identifier.

The repository’s existing full test command and relevant database reconciliation checks must also pass. Test output must not expose transaction-level or merchant-level personal data in the hand-off.

### Made by Hakim

Verification will include:

- existing CV/content validation;
- focused tests for the internal case-study action and route;
- a production Gatsby build;
- Playwright smoke coverage for page loading and navigation;
- desktop and mobile visual inspection;
- heading order, alternative text, figure captions, keyboard navigation and colour contrast;
- a final manual privacy and claims review.

## Completion and publication gates

Implementation is complete when the local synthetic generation and local website verification pass and the resulting diff is ready for review.

Completion does not authorise a commit, push, pull request, Vercel preview, deployment, publication, external message or sharing of any artefact. Each of those actions requires separate explicit approval.
